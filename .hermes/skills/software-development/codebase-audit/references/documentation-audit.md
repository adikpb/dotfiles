# Documentation / Contract Audit Against Source

Audits verify that docs (wiki pages, API contracts, bridge specs, plugin surfaces) match a vendored source clone, producing findings with dual citations (code `path:line` + doc line). Common in plugin-bridge projects where a wiki documents an implementation contract and subagents run **fresh** audits per task — recency of an edit is not accuracy.

## When to use
- Task says "audit <pages> against <clone>", "verify every load-bearing claim", "cite path:line for each finding".
- Before trusting a doc's code citations (line numbers drift across tags even when claims are true).
- Bridge/contract docs where a wrong claim silently becomes a designed-in bug.

## Workflow
1. **Inventory + read everything.** List target files, read each fully. Extract every load-bearing claim: method signatures, line cites, constants/enum sets, config keys+defaults, DB schemas, and *semantic* claims (persistence behavior, fail-open vs fail-closed, who fires what, veto vs observe).
2. **Batch-verify symbol locations.** One grep per page for `def <name>` / `class <name>` / constant assignments; compare exact lines. Batch independent greps into one turn — the whole audit can usually run in 4-6 tool turns.
3. **Verify signatures, not just presence.** Param lists matter (e.g. a plugin wrapper exposing fewer kwargs than the registry's `register()`).
4. **Verify semantics — hunt for INVERTED branches.** The worst doc rot is an if/elif whose branches the doc swapped (e.g. "tirith warning persists permanently" when code does `if session or (always and is_tirith): per-session-only; elif always: permanent`). Read both branches AND find what sets the discriminator flag (e.g. `is_tirith` vs `detect_dangerous_command` patterns).
5. **Verify delegation claims ("X via Y").** Search production call sites / importers repo-wide (exclude `tests/`) to find the real path. Two entry points are often *parallel*, not wrapping — "check_dangerous_command via check_all_command_guards" was wrong; they call the shared gate separately.
6. **Distinguish def-line cites from call-site cites.** `load_permanent_allowlist` def at :2528 but module-import call at :4350-4351 — a doc citing the import site is still correct; keep the distinction when judging.
7. **Distinguish handler-def lines from registry-registration lines** when docs cite "the tool" (handler at :786, `registry.register(...)` at :1793 — a doc citing 1793 is citing the tool registration).
8. **Check "hardcoded"/"always"/"never" claims** against literal strings (display_target template, deny-message text, poll counts).
9. **Verify read-path ownership (the "empty 200" trap).** A route can exist AND its session lookup can succeed AND the endpoint still returns nothing — when the read targets an aggregate/table written by a DIFFERENT engine than the one that ran the entity. Check: (a) which db table/aggregate the handler's service call reads; (b) which engine/module writes it (schema `durable:` markers, event publishers, projector tables); (c) whether the row lookup is a shared table that masks emptiness as HTTP 200 with empty body instead of 404. Real case: opencode v2 `history`/`context`/`message/:id` return empty for v1-run sessions — durable events and the session-message table are written only by the v2 core, while the v1 runner persists to legacy tables; the shared `SessionTable` hides it. "Route exists + 200" does NOT prove data flows; the docs claimed a v2 tail for sessions whose idle signal is v1-only.
10. **Report only code-backed findings**, dual cites, plus *missing load-bearing facts* if the task asks. State "NO NEW FINDINGS" explicitly when clean.
11. **Round-loop audits: verify the fixed-list first, then sweep for new drift.** Round N arrives with (a) a list of round-(N-1) findings said to be fixed — do NOT re-report any unless still wrong; verify each by grep/read before moving on — and (b) a list of NEW changes since the last round. **Briefed line numbers are PRE-fix numbers**: the fixer's edit shifts lines, so a brief saying "verify bridge.py:70 comment reads X" may find the comment at :75 (r6 real case) — grep the exact token/comment TEXT (content match), never trust the briefed line, and report the ACTUAL post-fix line in the ledger. Review each new change for consistency fallout: a route rename strands the old route in docs (`/session/{id}/message` → `/session/{id}/prompt_async` left wiki pages + idempotency bullets stale); a message-shape change strands flat-shape examples in wiki tables; a config-key addition strands dead keys in wiki examples. Structure the pass: verify each claimed fix → re-verify the clean surfaces → sweep for new findings. **Concurrent-editor triage**: when the maintainer may be editing WHILE you audit (many files modified), run `git status --short` FIRST — a briefed file that is modified gets re-read to see if the fix landed (report VERIFIED-FIXED); an unmodified TRACKED file is strong evidence the finding is still present verbatim. Caveat: git status is NO signal for git-ignored dirs (e.g. `wiki/` in some repos — round-2 Delta 3); those must always be read on disk. **Live-editor discipline when the tree is a moving target**: findings flip STILL-PRESENT→VERIFIED-FIXED between consecutive reads (r2r3 real case: events.py, bridge.py, tools.py, plugin-requirements.md, opencode-agent-registry.md, e2e_smoke.py, test_config.py all changed mid-audit). So: (a) start the slow evidence commands (pytest, ruff) in the background EARLY and RE-RUN them at the end — the report's evidence must reflect the final tree, and a mid-audit red suite that goes green before the final run becomes a caveat note, not a finding; (b) do a FINAL verification pass — one batched grep/sed snapshot of every finding's exact token + line number — immediately before writing the report, and cite THOSE line numbers, never the ones from your first read; (c) compound findings citing two sites get verified at EACH site separately — one can be fixed while the sibling stays stale (r2r3 F13: plugin-requirements.md:287 fixed to `register_tool(..., requires_env=...)` while hermes-plugin-surface.md:126 still claims manifest `requires_env:`); (d) a fix that lands between your grep and your report still counts as fixed only if the final snapshot confirms it. **Partially-applied fixes produce SELF-CONTRADICTORY bullets**: the fixer adds the new route as a side-note ("prompt_async is fire-and-forget") but never replaces the old route name in the main claim, so ONE bullet carries both the old token (line 76) and the new one (lines 80-81). Grep each suspicious bullet for BOTH tokens; a bullet containing both is a finding, not a fix.
12. **Stale-name dictionary sweep.** Encode every removed/renamed surface (old routes, config keys, method names, event shapes, tool names) as ONE regex alternation and sweep code, docs, tests, scripts. Typical hits: comments naming the old method (`wait_for_idle` after rename to `wait_for_complete`), wiki examples using a dead config key (`server_port` vs `port`), docs routing through old endpoints. When hits return exactly the requested limit, they may be truncated — re-run with a higher limit. Also check test-fake fidelity (fakes' method signatures vs the real client: create_session, prompt, messages, session_status, question_reply, iter_events) and that tests actually assert the new/changed config keys (silent coverage gaps are findings). Sweep scope includes scratch dirs: `.hermes/plans/` and similar can hold PRE-migration plans ("v2 API preferred with v1 fallbacks") describing the deleted architecture — stale-v2 residue that only a repo-wide (not wiki-only) sweep finds.
13. **Residue classification: classify every hit, don't just list it.** For a "sweep for remaining v2/old-route residue" task, bucket each hit:
    - **CODE_PATH** — live v2/old-surface calls in `.py` (after a migration there should be NONE; grep `/api/` and the old route tokens in code, tests, scripts). Tests that ASSERT the old surface is ignored (e.g. `test_events.py` frames `permission.v2.asked` / `question.v2.asked` / `session.next.stop` and asserts NO dispatch fires) are deliberate guards — EXPLANATORY, not CODE_PATH.
    - **Build-artifact false positive (`.pyc` caches)** — `__pycache__/*.pyc` compiled BEFORE the migration can still contain old-surface strings (`permission.v2.asked`, `active_sessions`, `session.next.stop`) long after the source was rewritten. They are INERT: Python validates each pyc against its source's mtime+size, so a pyc OLDER than its `.py` is never imported and is regenerated on the next run. Before reporting, `ls -laT` the pyc vs its source (source newer = safe); classify as a low/hygiene note (`rm -rf __pycache__`), never CODE_PATH. Real case: r2r1 — sources Aug 12 > pycs Aug 11.
    - **STALE_DOC** — a doc presents the old surface as what the system CURRENTLY does ("the plugin drives POST /session/{id}/message"). Medium when it misstates the primary route; low for: **live-target** stale version stamps ("verified against live opencode 1.18.13" / "E2E-verified … against live opencode 1.18.13" while the current README/live stamp is v1.18.16) — clone-tag references (vendored clone v1.18.13) are NOT this, they are correct; field-name drift (doc says `messageID`, code sends `id`), and claimed-but-unwired behavior (doc says "send a fresh messageID" but no caller passes one).
    - **EXPLANATORY** — doc describes the EXTERNAL server's own surface with explicit markers ("server reference only / not used by the plugin", "v2 (reference only, dropped <date>)") — correct, no action. A same-class page that got the two routes RIGHT (message-injection.md: "`POST /session/{id}/message` (legacy), waits for turn; `prompt_async` (underscore) enqueues without waiting") is the model for the fix — cite it as the pattern.
    - **HISTORICAL-LOG** — dated changelog/plan/resolved-questions records (log.md, `.hermes/plans/*`, sections headed "DELETED <date>") — no action, BUT a historical section's CURRENT-state parenthetical ("prompt() now does X via <old route>") is still a finding even inside history. Superseded guidance in dated "Resolved questions" bullets is HISTORICAL-LOG (annotate-superseded fix, not rewrite).
    - **Grep false-positive classes in the residue sweep** (filter, don't report): version stamps that are **clone/source-tag** references (`v2026.8.3`, `v1.18.13` when framed as the vendored clone / source code, e.g. "vendored audit clone is v1.18.13", "verified in the v1.18.13 clone", `@opencode-ai/sdk … v1.18.13`) — these are legitimately pinned to a tag and must NOT be flagged; config-field names that merely contain the keyword (`engines.opencode` semver field), unrelated identifiers (`context_engine/` dirs, "send_message engine"). **Exception — LIVE-target version stamps are STALE_DOC low, not false-positives**: any doc that names a *live* / E2E-verified version that contradicts the current README/live stamp (e.g. "E2E-verified … against live opencode 1.18.13" while the README says v1.18.16) reads as the current verified target and must be flagged. A bare-keyword regex hits all of these; classify them explicitly so the ledger shows they were seen and dismissed.
    - **Frontmatter date consistency (low STALE_DOC).** Pages that gained a dated banner/rewrite must carry `updated:` ≥ that date — check the frontmatter of every banner-annotated page. Real case (r4): plugin-requirements.md and opencode-permissions.md added 2026-08-11 v1-only banners but kept `updated: 2026-08-09`, while sibling session-reading.md was correctly bumped to 2026-08-11. Fix is a one-word date bump, but a reader trusting frontmatter places the page pre-migration.
    Report the ledger with counts per bucket so the parent sees the sweep was exhaustive (explicit FALSE-POSITIVE classes included — Delta 2).

## Pitfalls
- **Same-named files across packages are citation traps.** Monorepos frequently have `index.ts`/`hooks.ts`/`plugin.ts` in several packages (real case: `packages/plugin/src/index.ts` = plugin type contract vs `packages/opencode/src/plugin/index.ts` = loader/getLegacyPlugins/applyPlugin). Always cite (and verify against) the FULL path — a wiki page that says "plugin/index.ts:112" is ambiguous and probably wrong for one of the two.
- **Findings come in three classes, not two.** (a) contradiction (code disproves the claim), (b) omission (load-bearing fact missing), (c) incomplete-list (claim true as far as it goes, but a list it presents as exhaustive is not — e.g. generated SDK group lists, Tui method lists, config-key lists). Class (c) is low severity but still a finding; report it with the omitted items cited. Generated-code lists (`types.gen.ts`, `sdk.gen.ts`) are exhaustive by construction, so they are the reference corpus for list-completeness checks.
- **Generated files are line-stable anchors; hand-written cites drift.** `types.gen.ts:2601`, `:1226` etc. were exactly right at tag v1.18.13; hand-written prose cites (e.g. "index.ts:74-81") drifted a few lines. When a cited line is off by 1-10, re-derive with grep instead of flagging a contradiction.
- **Budget exhaustion mid-audit.** 10-page audits can exceed the tool-iteration cap. Batch aggressively (read all pages first, then terminal greps over file sets rather than per-file read_file), and if you cannot finish, close with an explicit list of which pages/claim-groups remain UNVERIFIED — never report a clean bill on what you didn't open.
- **Binary-file false positive:** `read_file` may flag clean UTF-8 markdown as binary (NUL/long-line heuristic). Recover with `file <path>` + `cat -v` and continue — don't skip the page.
- **Line cites drift across tags:** call out separately whether a claim is wrong in line number only vs wrong in substance.
- **Huge inline greps with command substitution** (`sed -n "$(grep -n ...)"`) can trip terminal parser limits — use search_files for content searches instead. Same for LONG single-line alternation greps with embedded quotes/escapes: the parser hard-BLOCKS them without executing (exit -1, "command parser limit or malformed executable payload") — re-issue the identical pattern via `search_files` (ripgrep-backed) and it runs fine. r4 real case: a 20-alternation `grep -rniE "V2Collapser|detect_engine|...|/api/"` over code+tests was blocked; the same regex in search_files returned in one call.
- **Semantic inversion is the highest-value finding.** Persistence/allowlist/approval docs are where if/elif branches get swapped in prose.
- **Don't quote module docstrings wholesale** — verify each sentence you plan to cite.
- **Verify "only consumer in-tree" claims** with a repo-wide search before repeating them.
- **Grep negatives get cross-checked.** In the hermes-opencode audit, `search_files` returned 0 matches for plain-word patterns in `tools/approval.py` (`is_tirith`, `save_permanent_allowlist`) while anchored regexes matched, `read_file` visibly showed the strings, and terminal `rg` matched instantly. A false negative on "does X exist" poisons the audit. Doctrine: when an audit-critical grep comes back empty (or terminal echo looks garbled — identifiers once echoed mangled), re-grep the same pattern with a second tool before concluding absence.
- **Prior-audit findings drift when the page is edited.** On a fresh re-audit, never trust a prior audit's line cites — re-locate each open claim by grepping its distinctive wording (e.g. "via `check_all_command_guards`"), not by its old line number. The hermes-opencode wiki fixed finding #1 (tirith) but the same edit shifted lines and left sibling finding #2 still wrong, now at 109-111 instead of 107-111. Fixing one finding does not fix its neighbors; reconcile the reference corpus's open-findings list against the CURRENT page text every pass.
- **Machine-validated output contracts: the final response must be ONLY the JSON.** When a task ends with "your FINAL response must be a single JSON object that validates against this JSON Schema", emit nothing else in that message — no summary paragraph before or after, no trailing report (a ```json code fence is tolerated; prose is not). Trailing prose makes the validator reject with `Extra data: line N column 1 (char M)`; malformed JSON (unterminated dict, stray text) bounces with `Expecting ':' delimiter: line 1 column N (char M)` — both cost a full re-emit, and the re-emit must REDO the work (the rejected output is lost; the round-4 JSON bounce was the malformed variant). Obey the schema's counting semantics too: if the contract says `total_findings` counts only NEW/STILL-PRESENT issues, verified-fixed items go in the /tmp report file, NOT in the findings array. Write the human-readable report to the /tmp file the task named; the JSON object is the only channel back to the parent.
- **read_file dedup can hide content that is not actually in context.** After a compaction, read_file may answer "File unchanged since last read" and point at an earlier result whose content you no longer have — looping read_file gets nowhere. Re-read with terminal `sed -n` / `grep -n` (or execute_code) to force fresh content instead.
- **Verification greps: `;` separators, single-quoted patterns.** Multi-finding verification chained with `&&` stops silently at the first no-match grep (exit 1 kills the chain — the r2r3 F8/F9 check returned nothing and F10/F12/F13 greps never ran), and backticks inside double-quoted patterns execute as command substitution (a `grep -n "Message\` = ..."` broke its own chain). Chain with `;`, single-quote patterns, or use search_files. Re-run the truncated remainder instead of assuming the first segment covered it.
- **Bare code defaults are audit targets even when latent.** A module-level default that differs from the documented config default (read.py `limit = 40` vs config `tail_size = 8`) is a finding even if every production call site passes an explicit value today — it is the documented contract for bare calls.
- **Verify external-system claims against the clone BEFORE flagging.** A wiki claim that contradicts the audited repo's own code may still be correct about the OTHER system it references. Real case: R7's "allowlist entries persist with a `plugin_rule:`-prefixed pattern" looked wrong given the plugin passes an explicit `opencode/<permission>/<hash>` rule_key — but hermes-agent's `tools/approval.py:3357` always builds `pattern_key = f"plugin_rule:{key_suffix}"` regardless of rule_key, so the claim was right and the finding was dropped. For claims about vendored deps (`.slim/clonedeps/...`), grep the clone first. A dropped false finding is as valuable as a confirmed one.
- **Severity calibration for docs-vs-code audits.** Docs/comment-only mismatches are cleanup/nit, never bug — the code is authoritative (and the test suite ran green). Merge same-file same-root-cause lines into one finding with a line range. Config-surface checks are BIDIRECTIONAL: undocumented keys AND documented-but-dead keys (a wiki example using a removed key name is a finding).
- **Repo-root sweeps explode when a venv/vendor tree lives inside.** `find`/`grep` from the repo root with `.venv/` and `.slim/clonedeps/` present dumps megabytes of noise (a bare `find` here returned ~2.4 MB). Always exclude `.venv .slim node_modules __pycache__ *.egg-info .git` (grep: `--exclude-dir=…`) in inventory and sweep commands; include them deliberately only when the task is about build artifacts.
- **execute_code: import every hermes_tools symbol you use.** Each script runs in a fresh interpreter — `from hermes_tools import read_file, terminal, search_files` must list every helper the body calls, or you hit a mid-script `NameError` on the first read (r2r1 real case). Keep the import line complete even when a batch is "mostly terminal".
